# Ide Agent LD/FBD 本地业务补全规则规范

版本：1.0  
状态：项目基线  
适用模块：`@ide-agent/core` 本地 LD/FBD suggestions  
参考样例：时间戳形式的图 JSON/TXT，例如 `1785977174111.txt`

## 1. 文档目的

本文定义 Ide Agent 在用户选中 LD/FBD 节点或插入点后，如何依据当前图拓扑、变量、功能块、区段说明和 POU 上下文生成本地建议。

本文回答四个问题：

1. 什么证据足以触发某类建议。
2. 哪些条件必须满足后才能把建议作为可应用候选返回。
3. 多个拓扑合法候选如何按业务价值排序。
4. 哪些场景必须禁止猜测、降级为普通拓扑建议，或留待后续设备模型和控制框架能力处理。

本文不是 IEC 标准全文、功能安全认证依据、前端 Patch 协议或图编辑器实现说明。

## 2. 标准边界

本项目以 IEC 61131-3 的语言和执行语义为基础。IEC 61131-3:2025 定义了 ST、LD、FBD，以及用于组织程序和功能块内部结构的 SFC。规则中的触点、线圈、函数、功能块、数据类型和端口方向必须遵守目标运行时对 IEC 61131-3 的实现。

本地建议不等于标准符合性证明，也不等于机器或过程安全验证。IEC 61131 系列对功能安全 PLC 另有 IEC 61131-6；机器安全相关控制系统还需要适用的安全生命周期、风险评估、验证和行业规范。本项目不得把普通图建议描述成安全功能的设计、认证或验证结果。

参考依据：

- IEC 61131-3:2025，Programmable controllers - Part 3: Programming languages  
  https://webstore.iec.ch/en/publication/68533
- IEC TR 61131-8:2017，IEC 61131-3 语言应用和实现指南  
  https://webstore.iec.ch/en/publication/33021
- IEC 61131-6:2012，Functional safety  
  https://webstore.iec.ch/en/publication/4555
- PLCopen Motion Control，运动控制功能块、状态机和一致性规则  
  https://www.plcopen.org/standards/motion-control/

## 3. 规范用语

- **必须（MUST）**：违反即不得返回可应用建议。
- **应当（SHOULD）**：通常应遵守，只有存在明确项目证据时才能偏离。
- **可以（MAY）**：可选增强，不影响基础合法性。
- **硬过滤（hard filter）**：候选不满足条件时从候选集移除。
- **软排序（soft rank）**：候选仍然合法，只调整优先级。
- **降级（fallback）**：业务证据不足时保留拓扑建议，不生成具体业务结论。

## 4. 当前运行时能力

### 4.1 输入

当前 Core 接收：

- `diagramPath`
- `segmentId`
- `selectedNodeId`
- `selectedInsertionPointId`
- `selectedVar`
- `focusQuery`

图文件名属于运行时输入。时间戳文件只作为真实样例，规则不得写死文件名、区段 ID 或节点 ID。

### 4.2 可用证据

当前可读取：

- 焦点节点类型、变量名、数据类型、作用域、功能块类型和实例名。
- 功能块输入输出端口名称和值。
- 当前节点的直接或最近可显示上下游节点。
- 当前区段的 `label`、`note`、节点、分支和输出状态。
- 当前 POU 的变量名、类型、作用域、标签、备注和注释。
- `st-library-info` 中目标函数或功能块的真实类型和端口。

当前不可可靠获得：

- 设备模型和经过确认的设备 ID/角色映射。
- SFC、状态机、设备 FB、配方或 AxisController 对命令路径的所有权。
- 项目安全需求、SIL/PL、风险评估和安全功能验证状态。
- 变量单位、量程、采样周期和持久化策略。
- 用户明确接受或拒绝过的历史建议。

### 4.3 当前可生成内容

当前一条 suggestion 只新增或替换一个节点：

- 常开、常闭、上升沿、下降沿触点。
- 普通、置位、复位线圈。
- 一个函数或功能块。

需要同时新增多个节点、变量和连接的业务模板属于后续能力，当前不得伪装成单节点建议。

## 5. 决策流水线

本地建议必须按以下顺序处理：

1. **输入校验**：图文件可读取、JSON 可解析、焦点可定位。
2. **拓扑候选生成**：根据串联、并联、分支边界、插入点和输出状态生成候选。
3. **拓扑硬过滤**：移除重复候选、非法重复输出和无法落图的边界组合。
4. **业务证据提取**：从焦点、邻居、区段和 POU 提取规范化术语与数据类型。
5. **业务规则匹配**：只执行 `status=active` 的规则，并检查焦点类型、术语、数据类型、模式和位置约束。
6. **库校验**：具体函数或功能块必须存在于 `st-library-info`；不存在时不得返回伪造端口。
7. **业务替换和排序**：将通用功能块候选替换为匹配的具体库元素，并应用可解释的分值。
8. **降级**：没有足够业务证据时只返回可确定类型的普通拓扑建议；不得把通用功能块槽位随机实例化为某个函数或功能块，变量保持 `???`。
9. **审计输出**：业务增强候选可以携带规则 ID、分值等级和原因；分值不是正确率或概率。

## 6. 证据强度

业务证据按局部性分级：

| 证据来源 | 默认权重 | 说明 |
| --- | ---: | --- |
| 当前焦点节点 | 4 | 最强证据 |
| 直接或最近上下游节点 | 3 | 强局部证据 |
| 当前 segment | 2 | 区段名称、备注和本区段节点 |
| 当前 POU | 1 | 只能增强已存在的局部证据，不能单独触发业务规则 |

规则不得仅因为同一 POU 中存在 `Fault`、`Axis` 或 `Timer` 等变量，就把无关区段判定为故障、运动或定时场景。

## 7. 规则文件模型

机器规则文件使用三类内容：

### 7.1 `libraryRules`

用于把通用功能块候选替换为具体 IEC/PLCopen/运行时库元素。活动规则支持：

- `termsAny`、`termsAll`、`excludedTerms`
- `focusKinds`
- `requiredAnyDataTypes`、`requiredAllDataTypes`、`excludedDataTypes`
- `candidateNames`
- `allowedModes`、`allowedPositions`
- `preferredModes`、`preferredPositions`
- `baseScore`
- `reason`、`fallback`

### 7.2 `rankingRules`

用于对已经拓扑合法的触点、线圈、函数和功能块候选进行软排序，不直接改变连接边界。

### 7.3 `plannedRules`

记录重要但当前证据或输出能力不足的业务需求。`plannedRules` 不参与运行时匹配，必须写明缺少的能力和当前降级行为。

### 7.4 活动规则字段语义

| 字段 | 类型 | 执行语义 |
| --- | --- | --- |
| `id` | string | 稳定且唯一的规则标识；修改显示文案时不得随意更换 ID。 |
| `status` | string | 只有 `active` 参与运行时；其他值不执行。 |
| `termsAny` | string[] | 至少一个术语必须出现在焦点、邻居或当前 segment。 |
| `termsAll` | string[] | 每个术语都必须有局部证据；POU 证据不能单独满足。 |
| `excludedTerms` | string[] | 任一排除术语有局部证据时规则失败。 |
| `focusKinds` | string[] | 焦点节点类型白名单，例如 `contact`、`FBDCompartment`、`editRect`。 |
| `requiredAnyDataTypes` | string[] | 当前 segment 至少存在一种指定数据类型；`NUMERIC` 表示 IEC 整数或浮点类型族。 |
| `requiredAllDataTypes` | string[] | 当前 segment 必须同时具有全部指定数据类型。 |
| `excludedDataTypes` | string[] | 出现任一类型时规则失败。 |
| `candidateNames` | string[] | 候选名称；必须能在运行时复制的 `st-library-info-data.json` 中精确查到。 |
| `allowedModes/Positions` | string[] | 硬约束；当前拓扑候选不在集合中时规则失败。 |
| `preferredModes/Positions` | string[] | 软偏好；只加分，不改变候选合法性。 |
| `baseScore` | number | 规则内部的相对优先级，不是概率。 |
| `reason` | string | 面向审计和维护者的业务依据。 |
| `fallback` | string | 前置条件不足时的明确降级行为。 |

示例：

```json
{
  "id": "T01-ton-on-delay",
  "status": "active",
  "termsAll": ["timer", "onDelay"],
  "excludedTerms": ["offDelay", "pulse", "safety"],
  "requiredAnyDataTypes": ["BOOL", "TIME"],
  "candidateNames": ["TON"],
  "allowedModes": ["functionBlockAfter", "functionBlockBefore"],
  "preferredPositions": ["behind"],
  "baseScore": 100,
  "reason": "通电延时、持续确认或超时检测使用 TON。",
  "fallback": "无法确认延时类型时不强行选择具体定时器。"
}
```

`termPatterns` 负责把中英文名称、标签和备注映射到规范化术语。每个术语使用两类匹配器：

- `literalPatterns`：忽略大小写的字面包含匹配，适合中文业务表达和自然语言短语。
- `regexPatterns`：使用固定的 `iu` 标志执行正则匹配，适合 IEC 标识、变量命名和分隔符变化。

示例：

```json
{
  "term": "onDelay",
  "literalPatterns": ["on delay", "通电延时", "延时启动"],
  "regexPatterns": [
    "(?:^|[^a-z0-9])on[_\\-.\\s]*delay(?:$|[^a-z0-9])"
  ]
}
```

`Stop_On_Delay_Timer` 由正则识别为 `onDelay`，但其中 `Stop` 末尾的 `tp` 不会误识别为脉冲术语。正则在规则加载时统一预编译；非法表达式只跳过该表达式并输出诊断，不中断本地建议。修改模式时必须同时补充正例和误命中反例。

规则结构可以扩展，但破坏兼容性的字段变更必须提升 `schemaVersion`。Core 继续读取旧版顶层 `rules` 作为迁移兼容；新规则只能写入 `libraryRules` 或 `rankingRules`。

## 8. V1 可执行规则

### 8.1 定时器

#### T01 TON 通电延时

- 触发：通电延时、延时启动、等待稳定、持续有效确认、超时检测。
- 必须：局部存在 BOOL 条件或定时器上下文，目标库存在 `TON`。
- 推荐：在条件后或合法功能块位置插入 `TON`。
- 排除：明确为断电延时或固定脉冲；仅 POU 其他区段出现定时器。
- 降级：无法确认延时类型时使用通用 timer 规则，不强行唯一选择 TON。

#### T02 TOF 断电延时

- 触发：断电延时、延时停止、停机后继续运行、冷却/润滑/抽风后运行。
- 必须：局部存在停止或失效语义，目标库存在 `TOF`。
- 排除：延时启动、等待稳定、超时报警。

#### T03 TP 脉冲

- 触发：固定脉冲、单次输出、点动脉冲、保持指定时间。
- 必须：存在 BOOL 触发语义，目标库存在 `TP`。
- 提示：持续 TRUE 的来源可能还需要边沿功能块；当前单节点 suggestion 不同时生成 `R_TRIG + TP`。

### 8.2 边沿

#### E01 R_TRIG

- 触发：上升沿、按下瞬间、仅执行一次、启动脉冲。
- 必须：局部存在 BOOL 信号，目标库存在 `R_TRIG`。
- 排除：已经选中或相邻存在等价上升沿节点，避免重复边沿化。

#### E02 F_TRIG

- 触发：下降沿、松开瞬间、失效瞬间、周期结束。
- 必须：局部存在 BOOL 信号，目标库存在 `F_TRIG`。

### 8.3 计数器

#### C01 CTU

- 触发：上计数、计件、累计次数、产量、批数。
- 必须：局部存在计数事件语义，目标库存在 `CTU`。
- 提示：持续电平是否需要边沿转换由目标运行时端口语义和图上下文决定。

#### C02 CTD

- 触发：倒计数、剩余数量、库存扣减。
- 必须：局部存在减计数语义和预置值需求。

#### C03 CTUD

- 触发：进出、加减、入库出库等双向计数。
- 必须：局部同时存在增加和减少两类事件证据。
- 排除：只存在单方向计数证据。

### 8.4 锁存和复位

#### L01 SR

- 触发：置位优先、故障/报警锁存、启动保持。
- 必须：局部存在 Set 与 Reset/清除语义之一，并且明确需要保持状态。
- 排除：普通 `Fault` 单词本身不足以证明需要新锁存；已有状态机所有权时当前只能降级提示。

#### L02 RS

- 触发：复位优先、停止优先、受控清除。
- 必须：局部存在 Reset/Stop/Ack 语义，并且明确需要保持状态。

### 8.5 数值、PID 和字符串

#### N01 比较和限幅

- 比较候选：`GT`、`GE`、`LT`、`LE`、`EQ`、`NE`。
- 限幅候选：`LIMIT`、`MIN`、`MAX`。
- 必须：局部存在数值数据类型以及明确的比较或限幅意图。
- 排除：类型未知或只有 BOOL 信号。

#### P01 PID

- 触发：PID、闭环、调节、控温、控压、控流、液位调节。
- 必须：局部同时存在数值类型以及 SP、PV、MV/输出角色证据，目标库存在 `PID`。
- 排除：缺少任一角色、单位未知且存在明显混用风险、仅出现 `PID` 名称但无回路变量。
- 说明：当前只能推荐一个 PID 节点，不能证明参数整定、采样周期或无扰切换正确。

#### STR01-STR05

- `LEFT`：字符串左取。
- `RIGHT`：字符串右取。
- `MID`：字符串中段截取。
- `CONCAT`：字符串拼接。
- `FIND`：字符串查找。
- 必须：局部存在 `STRING`/`WSTRING` 数据类型和对应明确意图。
- 排除：只出现自然语言“左/右/查找”但没有字符串证据。

### 8.6 运动控制

#### MC01 通用准入

所有 `MC_*` 候选必须同时满足：

- 局部存在 `Axis`、`AXIS_REF`、`MC_*` 或明确运动控制语义。
- 目标元素存在于当前 `st-library-info`。
- 当前 suggestion 只推荐单个运动功能块，不生成并行命令协调逻辑。

#### MC02-MC08

- 轴使能：`MC_Power`
- 轴复位：`MC_Reset`
- 回零：`MC_Home`
- 绝对定位：`MC_MoveAbsolute`
- 相对移动：`MC_MoveRelative`
- 速度运行：`MC_MoveVelocity`
- 停止：按明确意图推荐 `MC_Stop` 或 `MC_Halt`

普通设备故障或普通 `Reset` 不得触发 `MC_Reset`。没有轴证据时必须硬过滤全部 `MC_*` 候选。

### 8.7 输出节点和线圈

- 有逻辑节点但无输出节点时，应提高输出线圈候选优先级。
- 下游已经存在输出节点时，不得重复添加输出线圈。
- 选中线圈时可以推荐普通、置位、复位线圈互换，但业务语义只影响排序，不自动改变量名。
- 报警、故障、运行等关键词不能单独决定使用普通、置位还是复位线圈；必须结合区段语义和现有线圈类型。

## 9. 生产级硬约束

以下约束优先于所有业务评分：

1. 建议必须保持合法拓扑和端口方向。
2. 具体函数或功能块必须存在于当前库数据。
3. 要求字符串、数值、TIME 或 `AXIS_REF` 的规则必须有相应局部数据类型证据。
4. 不得跨设备自动绑定变量；当前没有可靠设备 ID 时变量保持 `???`。
5. 不得自动生成急停、安全门、光栅、STO 或其他安全信号旁路。
6. 不得声称建议满足 SIL、PL 或安全标准。
7. 不得把普通 Fault/Reset 映射为 `MC_Reset`。
8. 不得把有状态功能块当作可自由交换的纯 BOOL 条件。
9. 只有 POU 全局弱证据时不得触发具体业务功能块。
10. 需要多个新增节点才能成立的逻辑模板不得作为单节点可应用建议返回。

## 10. 软排序原则

在硬约束通过后，按以下顺序排序：

1. 当前焦点和直接邻居的业务证据。
2. 当前区段 `label/note` 和局部数据类型。
3. 与建议位置、模式和焦点节点类型的匹配程度。
4. 具体功能块规则优先于宽泛业务规则。
5. 当前 POU 只作为局部证据的增强项。
6. 拓扑完成度，例如半成品回路优先补输出。

业务分值只用于相对排序：

- `high`：满足具体意图和关键前置条件。
- `medium`：业务方向可信，但仍需要用户补变量或参数。
- `low`：主要依据拓扑或宽泛关键词。

## 11. 上下文不足和失败策略

- 焦点不存在：返回 `undefined`，不猜测其他区段。
- 图无可建议节点：返回 `noSuggestion`。
- 无业务术语：保留触点、线圈等可确定类型的拓扑候选，不返回未确定类型的通用功能块槽位。
- 库元素不存在：跳过该具体功能块候选，不伪造端口。
- 数据类型不足：跳过要求类型证据的规则。
- 设备归属不明：不自动选择实际变量。
- 控制框架所有权不明：不声称应在状态机外或状态机内实现。

## 12. V2 规划规则

以下规则有业务价值，但当前不应进入活动匹配：

| 规则族 | 缺少能力 | 当前降级 |
| --- | --- | --- |
| 同设备命令/反馈/故障关联 | DeviceModel、设备 ID 和角色映射 | 不自动选变量 |
| 电机/阀门/气缸完整模板 | 多节点 suggestion 和模板实例化 | 只返回单节点拓扑候选 |
| 状态机/SFC/设备 FB 所有权 | 控制框架元数据和公开接口 | 不做所有权结论 |
| 反馈超时和通信看门狗 | 命令-反馈关系、TIME 参数、多节点模板 | 可推荐单个 TON，但不生成完整模板 |
| 安全许可和复位前置 | 安全需求模型和验证状态 | 不自动旁路，不声称安全符合性 |
| PID 工程化配置 | 单位、量程、采样周期、参数和模式 | 只在强证据下推荐 PID 节点 |
| 计数持久化 | RETAIN/PERSISTENT 和生命周期策略 | 不自动决定持久化 |
| 项目模板复用 | 模板库、版本、适用条件和角色映射 | 不召回项目模板 |

## 13. 验收要求

每条活动规则至少需要：

- 一个正例：满足全部前置条件并命中正确候选。
- 一个反例：缺少关键证据时不命中。
- 一个冲突例：存在排除证据时不命中。
- 一个拓扑例：业务匹配但位置非法时不得返回。
- 一个库例：库中无元素时不得伪造候选。

建议的项目级回归场景包括：

1. 延时启动选择 TON。
2. 延时停止选择 TOF 而不是 TON。
3. 固定脉冲选择 TP。
4. 普通 Fault/Reset 且无轴证据时不出现 MC_Reset。
5. `AXIS_REF + Reset` 时允许 MC_Reset。
6. PID 缺少 SP/PV/MV 时不出现 PID。
7. STRING 左取时选择 LEFT，数值“左侧”场景不选择 LEFT。
8. 双向计数场景选择 CTUD，单向场景不选择 CTUD。
9. 下游已有输出时不重复补线圈。
10. 只有 `???` 时保持拓扑降级。

## 14. 规则治理

- 新规则必须先进入 `plannedRules`，完成证据、反例和回归测试后才能改为活动规则。
- 修改术语模式时必须检查常见英文子串误命中。
- 修改候选功能块时必须验证 `st-library-info` 中的类型和端口。
- 业务规则变更不得绕过拓扑硬约束。
- 规则文件、文档和测试用例必须在同一变更中保持一致。
- 真实时间戳图文件只能作为测试样例，不能成为运行时默认路径或规则依赖。
