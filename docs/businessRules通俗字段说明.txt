businessRules.json 通俗字段说明
===============================

适用版本
--------

本文对应当前 Ide-agent 项目中的 businessRules.json。
版本号、Schema 地址等一眼就能看懂、且不参与业务判断的字段不展开说明。


一、这个规则文件整体在做什么
----------------------------

businessRules.json 不是一份“看到关键词就直接插节点”的字典。
它把一次本地补全拆成几层判断：

    1. 从区段标题、备注、变量名、变量注释中识别业务词。
    2. 判断变量在业务中是什么用途，例如命令、运行反馈、故障、设定值。
    3. 判断多个变量是否属于同一个设备或同一个业务回路。
    4. 判断当前缺的是触点、线圈、定时器、运动功能块还是其他库元素。
    5. 检查推荐的功能块或函数是否真实存在，端口名称和类型是否正确。
    6. 过滤会绕过关键条件、重复已有能力或拓扑不合法的候选。
    7. 给剩余候选排序，并在证据可靠时生成业务文案。

例如用户选中“启动请求”触点时，引擎不会只看到“启动”两个字。
它还会检查同组变量中是否有设备就绪、故障、停止命令、运行输出等信息，
再决定应该推荐就绪常开触点、故障常闭触点、停止常闭触点还是普通结构节点。


二、多个规则都会用到的公共字段
------------------------------

下面这些字段会在多种规则里反复出现，这里统一解释一次。

1. id

规则的唯一名字，主要用于测试、日志和诊断，例如：

    "id": "T01-ton-on-delay"

它不参与业务匹配，也不是建议分数。

2. status

表示规则是否投入运行：

    active   当前会参与匹配
    planned  只是记录未来需求，当前不会执行

3. termsAny、termsAll、excludedTerms

它们判断当前上下文中识别出的业务术语：

    termsAny       列表中任意一个命中即可，相当于 OR
    termsAll       列表中每一个都必须命中，相当于 AND
    excludedTerms  任意一个命中就否决，相当于“出现这些词就别套本规则”

例子：

    "termsAll": ["timer", "onDelay"],
    "excludedTerms": ["offDelay", "pulse", "safety"]

通俗理解：必须能确认“这是定时”并且“这是通电延时”，同时不能是断电延时、
脉冲或安全逻辑，才可以使用这条规则。

这里的 timer、onDelay 不是直接在图上查找的文字，而是 termPatterns 识别后的内部术语。

4. anchorRolesAny、candidateRolesAny、chainRolesAny、requiredRolesAll

这些字段判断变量角色：

    anchorRolesAny    当前选中或动作锚点具备任意一种角色即可
    candidateRolesAny 可以作为待补全变量的角色范围
    chainRolesAny     当前整条局部链中至少出现一种指定角色
    requiredRolesAll  同一设备或回路中必须把列出的角色全部凑齐

例如：

    "anchorRolesAny": ["commandSignal"],
    "candidateRolesAny": ["readySignal", "faultSignal"]

表示当前锚点必须是动作命令，然后从同一设备中寻找就绪或故障变量作为补全候选。

5. acceptedDataTypes、requiredAnyDataTypes、requiredRoleTypes

这些字段都是类型限制，但使用位置不同：

    acceptedDataTypes     当前角色或端口允许哪些数据类型
    requiredAnyDataTypes  当前局部上下文至少出现其中一种类型或类型组
    requiredRoleTypes     某个回路角色必须是什么类型

例如 setpoint 只接受 REAL/LREAL，防止把 BOOL 开关误判成 PID 设定值。

6. candidateNodeType、candidateNames、blockTypes

    candidateNodeType  要新增的图形节点类型，例如 contact、negatedContact、coil
    candidateNames     要推荐的库元素名称，例如 TON、PID、MC_Stop
    blockTypes         一条角色规则或画像适用于哪些已有功能块

candidateNames 和 blockTypes 中的功能块/函数名称必须与 st-library-info-data.json 一致。

7. allowedPositions、preferredPositions、allowedModes

position 表示相对选中节点的位置：

    front          前串联
    behind         后串联
    outsideFront   整个并联结构外侧前串联
    outsideBehind  整个并联结构汇合后串联
    parallel       并联
    replace        替换当前节点

mode 表示建议以什么结构方式生成，例如：

    functionBlockAfter   在选中节点之后插功能块
    functionBlockBefore  在选中节点之前插功能块
    parallelBranch       新增并联分支
    outputFunctionBlock  在输出侧插功能块

字段区别：

    allowedPositions  硬限制，不在列表里的位置不能使用本规则
    preferredPositions 软偏好，位置符合时加分，但其他合法位置仍可能保留
    allowedModes      硬限制，候选生成方式必须属于列表

规则不会自己计算 startNodes/endNodes，连接关系仍由原拓扑算法生成。

8. priority、baseScore、termMultiplier

    priority        规则层级，通常先比较优先级
    baseScore       规则命中后提供的基础分
    termMultiplier  业务术语证据折算成分数时使用的倍率

priority 不是整个文件共用的一把尺子。
libraryRules 的 priority 只和库规则比较，contactPolarityRules 的 priority 只和极性规则比较。

最终 suggestions 的分数还包含拓扑分、业务证据分和业务链分，
所以不能只看某一条规则的 baseScore 判断最终顺序。

9. businessName、reason、fallback

    businessName  简短业务名称，例如“故障联锁”“反馈确认”
    reason        为什么推荐这条建议
    fallback      证据不足时应该怎样保守处理的说明

reason 和 fallback 不是匹配条件。

10. presentation

presentation 控制可靠业务建议最终显示的 title 和 text：

    "presentation": {
      "titleTemplate": "{placementAction} {businessName}常闭触点",
      "textTemplate": "{reason}；{placementText}。"
    }

常用占位符：

    {businessName}    规则配置的业务名称
    {reason}          规则配置的推荐原因
    {focusVar}        当前选中变量
    {actionName}      当前动作锚点或最终动作
    {candidateName}   候选功能块名称
    {candidateVar}    实际准备绑定的候选变量
    {placementAction} 前串联、后串联、并联等短语
    {placementText}   “建议在 X 后串联一个触点”这类完整位置说明
    {elementType}     常开触点、线圈、功能块等节点类型

模板使用了引擎不认识的占位符时，不会硬拼残缺文案，而是回退到原结构文案。


三、基础候选和数据类型
--------------------

1. enabled

控制业务库元素增强是否启用。
它不是“关闭所有建议”的总开关；即使关闭，基础拓扑建议仍可能返回。

2. defaultBlocks

通用功能块候选池，例如 TON、TOF、TP、CTU、CTD、SR、RS。

它的意思不是“每次都推荐这些块”，而是当基础拓扑允许插功能块时，
先从这里建立通用候选，之后还要经过 libraryRules、库存在性、端口和去重检查。

3. dataTypeGroups

把多个实际 IEC 类型合成一个方便复用的类型组。

例如：

    "NUMERIC": ["SINT", "INT", "DINT", "REAL", "LREAL", ...]

规则写 NUMERIC 时，就不需要每次把所有数值类型重新列一遍。

对象的键是自定义类型组名，值是这个组包含的真实类型。
当前常见组：

    NUMERIC  所有常用数值类型
    INTEGER  常用有符号和无符号整数
    ANY_INT  IEC 泛型整数能力
    FLOAT    REAL、LREAL 等浮点类型

4. typeCapabilities

把不同厂商或运行库中的实际类型归纳成一种业务能力。

例如：

    "MOTION_AXIS_REFERENCE": ["AXIS_REF", "AXIS_REF_SM3"]

只要局部变量出现其中任意一种类型，就认为具备“运动轴引用”能力。
MC_* 规则可以依赖 MOTION_AXIS_REFERENCE，而不用绑定某一种厂商轴类型。


四、业务术语识别
----------------

1. termPatterns

作用：把人写的各种表达转换成引擎统一认识的内部术语。

子字段：

    term             统一术语名称
    literalPatterns  普通字面包含匹配列表
    regexPatterns    正则表达式匹配列表

例子：

    {
      "term": "timer",
      "literalPatterns": ["timer", "定时", "延时", "超时"],
      "regexPatterns": ["(?:^|[^a-z0-9])(?:ton|tof|tp)(?:$|[^a-z0-9])"]
    }

“送料超时监控”会通过 literalPatterns 命中 timer。
“TON_Alarm”会通过 regexPatterns 命中 timer。
“XTON”不会命中上述正则，因为 TON 左边仍然是英文字母，不满足边界条件。

literalPatterns 适合中文和明确长词；regexPatterns 适合缩写边界、分隔符和多种写法。

2. derivedTerms

作用：不依赖文字，而是根据数据类型或类型能力补出业务术语。

子字段：

    term                     要补出的内部术语
    whenDataTypesAny         出现任意指定数据类型/类型组时触发
    whenTypeCapabilitiesAny  具备任意指定类型能力时触发

例子：

    {
      "term": "motion",
      "whenTypeCapabilitiesAny": ["MOTION_AXIS_REFERENCE"]
    }

当前区段存在 AXIS_REF 时，即使 label 没写“运动控制”，也能获得 motion 证据。

3. termImplications

作用：一个具体术语命中后，自动补出它所属的通用术语。

子字段：

    ifMatched  已经命中的术语
    alsoMatch  需要继续补充的术语列表

例子：

    onDelay -> timer
    countUp -> counter
    motionHalt -> motion

这样 TON 规则可以要求 timer + onDelay，而不用在每条规则中重复所有“定时”同义词。


五、变量在业务中是什么用途
--------------------------

1. variablePatterns

variablePatterns 不直接产生 suggestion。
它负责把变量识别成“实际值、设定值、命令、故障、反馈、许可”等角色，
供后面的回路签名和业务补全规则使用。

1.1 prefixRoles

根据变量名前缀判断角色。

子字段：

    prefix             变量名必须以什么开头
    role               命中后得到的业务角色
    controller         可选的控制器类别说明
    acceptedDataTypes  允许的数据类型

例子：

    Pid_Tank_Temp : PID

前缀 Pid_ 加上 PID 类型，可识别为 pidController。
这只是“存在 PID 控制器变量”的证据，不会仅凭名字再次推荐 PID。

1.2 suffixRoles

根据变量名后缀判断角色。

子字段：

    suffix             变量名必须以什么结尾
    role               命中后的业务角色
    acceptedDataTypes  类型硬约束

常见例子：

    Tank_Temp_PV : REAL        -> processValue，实际过程值
    Tank_Temp_SP : REAL        -> setpoint，目标设定值
    Tank_Temp_MV : REAL        -> manipulatedValue，调节输出
    Pump_Run_Permit : BOOL     -> permitSignal，运行许可
    Conveyor_Jam : BOOL        -> inhibitSignal，堵料阻断
    Pack_Batch_Done : BOOL     -> batchCompletionOutput，批次完成输出

如果 Tank_Temp_PV 是 BOOL，类型不符合，就不会确认成 processValue。

1.3 roleEvidenceRules

作用：当客户没有严格使用 _PV、_SP、_Fault 等规范后缀时，
综合变量名、区段标题、区段备注和变量注释判断变量用途。

每条角色规则的子字段：

    role               最终要确认的变量角色
    acceptedDataTypes  允许的数据类型，属于硬约束
    minScore           确认该角色至少需要多少证据分
    sources            可以从哪些文字来源收集证据

sources 中每项的子字段：

    source           来源字段，只能是 name、label、note、comment
    literalPatterns  字面匹配词
    regexPatterns    正则匹配式
    score            该来源命中后贡献的角色证据分

例子：

    TIC101_IN   REAL   注释：炉温实际值

变量名本身不规范，但 comment 命中“实际值”，得分达到 minScore，
所以可以识别为 processValue。

同一个来源命中多个同义词时只取该来源的最高分，避免一句注释重复加分。
不同来源可以累加，例如 name 和 comment 同时命中。

这里的 score 只用于确认变量角色，不是 suggestion 最终排序分。

1.4 physicalTerms

作用：识别变量或区段在处理哪一种物理量。

子字段：

    physical         统一物理量名称，例如 temperature、pressure、flow
    literalPatterns  物理量的普通写法
    regexPatterns    缩写或边界写法

例如 Tank_Temp_PV 可识别出 temperature，Pressure_SP 可识别出 pressure。
物理量用于区分回路，避免把温度实际值和压力设定值拼成一个 PID 回路。

1.5 当前常见角色用人话解释

    processValue          设备或过程当前实际测到的值
    setpoint              用户希望达到的目标值
    manipulatedValue      控制器算出的调节输出
    controllerOutput      已有控制器功能块的真实输出端口变量
    controllerParameter   Kp、Ti、Td 等控制参数
    commandSignal         启动、停止、执行等动作命令
    startCommand          明确的启动请求
    stopCommand           明确的停止请求
    resetCommand          人工复位或状态清除请求
    runFeedback           电机、输送线等设备已经运行的反馈
    completionSignal      动作完成、到位或功能块完成信号
    readySignal           设备已经准备好，可以接受命令
    faultSignal           设备故障或异常状态
    permitSignal          TRUE 时允许动作的正逻辑许可
    inhibitSignal         TRUE 时阻止动作的堵料、跳闸、禁用信号
    presenceSignal        有料、有工件、占位、入口/出口传感器
    alarmOutput           普通报警输出
    faultLatch            需要置位保持、之后人工复位的故障状态
    actionOutput          泵运行、阀打开、气缸伸出等执行输出
    batchCompletionOutput 批次完成的普通状态输出
    batchCompletionLatch  需要保持的批次完成状态
    axisReference         MC_* 功能块使用的轴引用
    conditionSignal       定时器或逻辑块的启动条件
    presetDuration        定时器预置时间
    deceleration          运动停止或减速使用的减速度参数
    modeSignal            自动、手动等工作模式
    selectionSignal       设备、工位或路径选择信号


六、从真实功能块端口判断变量角色
------------------------------

1. blockPortRoleRules

作用：如果变量已经绑定在功能块端口上，端口语义通常比变量名更可靠。

子字段：

    blockTypes  适用的功能块/函数名称
    ports       端口与业务角色的映射列表

ports 每项的子字段：

    port               真实端口名，大小写不敏感匹配
    direction          input、output 或 any
    role               该端口变量对应的一个角色
    roles              该端口同时对应多个角色时使用
    acceptedDataTypes  端口绑定变量允许的类型
    score              可选的结构证据分；端口证据通常属于高置信度

direction=any 主要用于 VAR_IN_OUT，例如 MC_* 的 Axis。

例子：

    TON.IN -> conditionSignal
    TON.PT -> presetDuration
    TON.Q  -> completionSignal
    TON.ET -> elapsedDuration

    MC_Stop.Axis    -> axisReference
    MC_Stop.Execute -> commandSignal
    MC_Stop.Done    -> completionSignal
    MC_Stop.Error   -> faultSignal

即使变量叫 X1，只要它真实绑定在 MC_Stop.Done 上，也能可靠识别成完成反馈。
端口不存在或类型不符时只跳过该角色映射，不会伪造端口。


七、运动功能块的触发模型
----------------------

1. motionCommandProfiles

作用：描述 PLCopen 运动块是“持续保持型”还是“上升沿命令型”，
以及哪些输出端口可以表示完成、活动、忙、故障和命令中止。

子字段：

    blockTypes                 本画像适用的运动块
    triggerModel               level 或 risingEdge
    triggerPort                Enable、Execute 等真实触发端口
    completionPorts            完成/到位输出端口名
    activePorts                活动/使能状态端口名
    busyPorts                  忙状态端口名
    faultPorts                 Error、ErrorID 等故障端口名
    abortedPorts               CommandAborted 等命令中止端口名
    locksAxisWhileTriggerTrue  触发输入保持 TRUE 时是否锁住该轴

例子：

    MC_Power:
      triggerModel = level
      triggerPort = Enable

表示 Enable 必须持续保持，不能当成 Execute 上升沿命令使用。

    MC_Stop:
      triggerModel = risingEdge
      triggerPort = Execute
      locksAxisWhileTriggerTrue = true

表示 Execute 上升沿启动停止命令，而且 Execute 保持 TRUE 时会阻止轴接受新命令。

这些字段只描述程序静态结构，不代表运行时某个端口当前为 TRUE。


八、判断多个变量是否属于同一业务回路
----------------------------------

1. loopSignatures

作用：把多个变量角色组合成完整业务回路证据。

例如 PID 回路通常需要：

    实际值 processValue
    设定值 setpoint
    控制输出 manipulatedValue/controllerOutput

只有这些角色属于同一组，才可以认为“这套 PID 条件基本齐了”。

子字段：

    kind                       签名类型，completion 或 observed
    groupStrategies            判断变量属于同一组的方式和优先顺序
    requiredRolesAll           同组必须全部具备的角色
    requiredRoleTypes          每个角色允许的数据类型
    requiredPhysicalTerms      必须全部出现的物理量
    requiredPhysicalTermsAny   多个物理量中出现任意一个即可
    evidenceTermsAny           还需要出现的辅助业务术语，任意一个即可
    evidenceBlockTypesAny      端口证据必须来自哪些已有功能块
    targetBlockTypes           这套签名准备补全或确认的目标功能块
    missingRolesAny            completion 签名中，至少缺少其中一个角色才算“待补全”

1.1 kind

    completion  条件已经基本具备，但目标功能块或某个关键角色还缺失
    observed    已经从真实功能块实例及其端口中观察到完整关系

completion 才会用于“缺什么就推荐什么”。
observed 用于确认“这里已经有这套功能”，不能反过来再次推荐同类块。

1.2 groupStrategies

当前支持：

    groupId          输入数据明确给出的回路 ID
    deviceId         输入数据明确给出的设备 ID
    namePrefix       从规范变量名公共前缀推断同组
    fbInstancePorts  同一个功能块实例的端口绑定天然属于一组

优先使用明确的 groupId/deviceId 或真实功能块端口。
缺少这些结构化信息时，才使用变量名公共部分兜底。

“同组”不等于“同一个 POU 中的所有变量”。
同一个 POU 可以有 Tank01 温度回路和 Tank02 温度回路，它们不能混在一起。

1.3 PID completion 示例

    Tank01_Temp_PV : REAL
    Tank01_Temp_SP : REAL
    Tank01_Temp_MV : REAL
    区段文字包含“温度 PID”
    当前同组还没有 PID 功能块

可以满足：

    requiredRolesAll = processValue + setpoint + manipulatedValue
    requiredPhysicalTerms = temperature
    evidenceTermsAny = pid
    targetBlockTypes = PID

此时 libraryRules 才能据此推荐 PID。

如果 SP 缺失、MV 是 BOOL、三个变量属于不同 groupId，或者同组已经存在 PID，
这条 completion 签名都不应命中。

1.4 通用定时和运动示例

定时器 completion 可以要求同组已有 conditionSignal 和 presetDuration，但还没有 TON。

MC_Stop completion 可以要求同组已有 axisReference、commandSignal、deceleration，
并且还没有 MC_Stop，之后才允许推荐 MC_Stop。


九、设备命令、反馈、故障和动作闭环
--------------------------------

1. deviceLoopRules

作用：围绕一个明确动作命令，逐个补充同设备或同动作组中的许可、阻断、
就绪、故障、占位以及相反动作互锁。它仍然是每次补一个节点，不会一次生成整条回路。

独有字段：

    anchorTermsAny          动作锚点还需要命中的动作术语
    candidateNodeType       候选使用常开还是常闭触点
    oppositeActionCandidates 相反动作互锁的专门配置

其余 anchorRolesAny、candidateRolesAny、allowedPositions 等字段见公共字段说明。

例子：

    Pump01_Start_Cmd   启动命令
    Pump01_Ready       就绪反馈
    Pump01_Fault       故障信号

如果当前回路只有启动命令，规则可以渐进推荐：

    Pump01_Ready 常开触点
    Pump01_Fault 常闭触点

已经接入的变量不会重复推荐，不同 deviceId 的变量不会混用。

1.1 oppositeActionCandidates

作用：配置明确的相反动作对，例如开/关、伸/缩、正转/反转。

子字段：

    rolesAny     哪些角色可以成为相反动作候选
    pairs        相反动作术语对
    businessName、reason、presentation 该类建议的业务文案

pairs 每项：

    leftTerms   动作对左侧术语，例如 open
    rightTerms  动作对右侧术语，例如 close

例如当前动作是 Valve01_Open_Cmd，同设备存在 Valve01_Close_Cmd，
系统可以推荐把 Close 命令作为常闭互锁触点。

2. faultResponseRules

作用：当前条件已经明确是故障或超时时，补报警输出或故障锁存。

典型关系：

    faultSignal/timeoutSignal -> alarmOutput 普通线圈
    faultSignal/timeoutSignal -> faultLatch 置位线圈

重要字段：

    anchorRolesAny     哪些条件可以触发故障响应
    anchorTermsAny     还需要哪些故障/超时术语
    candidateRolesAny  寻找报警输出还是故障锁存变量
    candidateNodeType  coil 或 setCoil

没有可靠同组变量时，保留普通 ??? 输出建议，不跨设备猜报警变量。

3. faultResetRules

作用：当前有人工复位命令时，寻找同组中已经由 setCoil 锁存、
但还没有 resetCoil 清除路径的故障锁存变量。

典型关系：

    另一段：Pump01_Fault -> Pump01_Fault_Latched 置位线圈
    当前段：Pump01_Reset -> 缺少输出

系统可推荐：

    Pump01_Reset -> Pump01_Fault_Latched 复位线圈

candidateNodeType 在此类规则中是 resetCoil。
只有变量声明、没有真实置位线圈时不会推荐；已经有复位线圈时也不重复推荐。

4. actionLifecycleRules

作用：补齐动作从启动到保持、停止释放，以及计数完成输出的生命周期节点。

独有字段 kind 表示具体补全类型：

    selfHold               启动触点旁并联动作输出触点，形成自保持
    stopInterlock          在启动链前串联停止命令常闭触点
    latchedRelease         停止条件后补动作输出的复位线圈
    countCompletionOutput  计数完成后补普通批次完成线圈
    countCompletionLatch   计数完成后补需要保持的置位线圈

例子：

    Pump01_Start -> Pump01_Run 普通线圈

选中 Pump01_Start 时，可以推荐：

    与 Pump01_Start 并联 Pump01_Run 常开触点
    在启动链前串联 Pump01_Stop 常闭触点

前提是同一 POU 中存在真实动作输出，并且设备/动作归属能够确认。


十、常开和常闭触点怎么决定
------------------------

1. contactPolarityRules

作用：决定业务上下文中是否应该增加常闭触点候选，或者明确保持常开逻辑。

独有字段：

    polarity             normal 表示常开，negated 表示常闭
    excludedAnchorTerms  选中节点或直接邻居出现这些术语时否决
    anchorTermScope      excludedAnchorTerms 检查选中节点还是同时参考邻居

例子：

    Ready、Healthy、Permit_OK

通常表示 TRUE 时允许动作，优先使用常开触点。

    Fault、Stop、Jam、Trip

作为运行许可链中的抑制条件时，通常需要常闭触点，让故障或停止成立时切断回路。

极性规则不会删除基础常开候选，而是根据证据增加或提高常闭候选。
安全逻辑仍被 excludedTerms 中的 safety 排除，不能用普通规则代替安全设计。


十一、触点、线圈和沿的业务文案
----------------------------

1. nodeIntentRules

作用：候选节点已经生成后，判断这个触点、线圈、上升沿或下降沿在业务上是干什么的，
然后把“后串联 常开触点”升级成“后串联 反馈确认常开触点”等业务文案。

它不生成节点、不改变常开/常闭，也不改 startNodes/endNodes。

独有字段：

    nodeTypes             规则适用的候选节点类型
    positions             哪些插入位置可以使用这套业务说法
    actionRolesAny        最终动作锚点必须具备的角色
    chainRolesAny         当前链中至少出现的角色
    requireActionAnchor   是否必须找到明确动作输出或功能块
    minimumEvidenceCount  至少需要多少项一致证据

例子：

    当前链中存在 commandSignal + runFeedback
    候选节点是 contact
    证据数量达到 minimumEvidenceCount

则可以显示：

    title: 后串联 反馈确认常开触点
    text: 当前链路包含动作命令以及运行反馈，建议补充反馈确认条件……

如果只有一个模糊关键词、变量全是 ???、没有明确动作锚点，
系统继续使用原来的结构文案，不编造业务含义。


十二、防止重复推荐和绕过关键条件
--------------------------------

1. businessChainGuards

作用：业务链证据可靠时，过滤少量明确有风险的候选。
它不生成候选、不加分，也不重新计算拓扑。

子字段：

    parallelBypassProtectedRoles
        不能被新增并联分支直接绕过的角色。
        例如许可、就绪、故障、抑制和模式条件。

    relatedCapabilityIdentityRoles
        跨区段判断“是否同一设备/轴”时认可的身份角色。
        当前主要是 axisReference，并为 deviceReference 预留。

    identityScopedCapabilityBlockTypes
        同一设备身份通常只应存在一份的能力块。
        当前包括 MC_Power、MC_Reset、MC_Home。

    relatedCapabilityMinSharedReferences
        跨区段判断两个功能块属于同一能力时，至少需要共享多少个引用变量。

例子：

同一根轴已经有 MC_Power，就不应在其他区段因为“轴使能”文字再次推荐 MC_Power。
但同一根轴可以存在多个不同请求驱动的 MC_Stop/MC_Halt/Move 命令，
不能只因为 Axis 一样就把这些候选全部删掉。

如果选中节点是可靠的故障常闭联锁，系统也不应推荐一个并联支路把它直接绕过去。

2. businessChainEnhancement

作用：业务链已经可靠解析后，为已有业务证据的候选增加一小部分独立分数，
并增强 nodeIntentRules 的正文说明。它不负责生成候选。

分数字段：

    resolvedPresentationScore  完整业务链 + 已有业务文案时的链路分
    partialPresentationScore   部分业务链 + 已有业务文案时的链路分
    resolvedEvidenceScore      完整业务链 + 只有业务证据时的链路分
    partialEvidenceScore       部分业务链 + 只有业务证据时的链路分
    highConfidenceRoleBonus    选中节点具有端口等高置信度角色时的额外分

文案字段：

    nodeIntentTitleTemplate  业务意图标题模板
    nodeIntentTextTemplate   业务链正文模板

当前标题模板只保留：

    {placementAction} {businessName}{elementType}

不会再把已有区段 label 重复放到标题前面。

正文模板还可以使用：

    {chainName}    区段业务名称
    {selectedName} 选中变量或节点名称
    {actionName}   最终动作，例如 MC_Stop (Mc_Stop_Feed_Axis)
    {actionType}   最终动作类型
    {baseTitle}    nodeIntentRules 原始业务标题
    {baseText}     nodeIntentRules 原始业务说明

只有业务链 resolution=resolved、存在高置信度证据并能找到最终动作时，
才会使用完整链路正文。证据不足时业务链分为 0，并回退原文案。


十三、功能块和函数推荐
--------------------

1. libraryRules

作用：把已经识别的业务条件映射成 st-library-info-data.json 中真实存在的功能块或函数。

它是硬筛选层。条件不满足时，候选不会因为分数高就强行返回。

1.1 业务条件字段

    termsAny、termsAll、excludedTerms
        见公共字段说明。

    requiredAnyDataTypes
        当前局部至少存在其中一种可用数据类型或类型组。

    requiredTypeCapabilities
        当前局部必须具备指定类型能力，例如 MOTION_AXIS_REFERENCE。

    signatureRefsAny
        至少命中一个指定 loopSignatures。
        它用于表达“多个角色已经组成完整待补全关系”，比单个关键词可靠。

例子：

    signatureRefsAny = ["LS06-on-delay-missing-timer"]

表示只有同一定时回路的条件、预置时间等签名已经成立，才推荐 TON。

1.2 portRequirements

作用：推荐前检查候选库元素是否真的有需要的端口，并确认端口类型正确。

子字段：

    port                  端口名，例如 IN、PT、Q、Axis
    direction             input、output 或 any；省略时按 input 处理
    required              true 表示候选必须存在该端口
    acceptedDataTypes     该端口允许的数据类型/类型组
    allowCreateParameter  当前还没有对应输入变量时，是否允许把端口留作待绑定参数

例子：

    {
      "port": "PT",
      "required": true,
      "acceptedDataTypes": ["TIME"],
      "allowCreateParameter": true
    }

意思是 TON 必须真实存在 TIME 类型的 PT 输入；当前没有 TIME 变量时，
仍允许生成 TON，但 PT 需要用户后续绑定或创建参数。

输出端口只检查库中是否存在以及类型是否正确，不要求 POU 变量表提前声明输出变量。

1.3 候选和排序字段

    candidateNames      可能返回的真实库元素
    allowedModes        允许的生成方式
    preferredPositions  哪些合法位置更适合此业务块
    priority            库规则层级
    baseScore           同层级候选的基础分

例如定时语义模糊时，T00 可以同时给 TON/TOF/TP 较低优先级候选；
明确识别通电延时后，T01 只给 TON，并使用更高优先级和分数。

1.4 reason、fallback、presentation

    reason        命中后为什么推荐该块
    fallback      证据不够时应该保留什么保守行为
    presentation  可靠命中时显示的业务标题和正文模板

fallback 只是降级说明，不会自动执行另一套隐藏规则。


十四、普通候选如何排序
--------------------

1. rankingRules

作用：对已经合法生成的普通触点、线圈、沿等候选做软排序。
它不会创建候选、不会修改节点连接，也不会像 libraryRules 那样做硬筛选。

子字段：

    candidateNodeTypes  只给哪些节点类型加分
    positions           只给哪些位置加分
    termsAny/termsAll   需要哪些业务术语
    excludedTerms       出现哪些术语时不加分
    priority            多条排序规则命中时使用的规则层级
    baseScore           基础加分
    termMultiplier      术语证据的倍率

例子：

    当前识别到 reset
    candidateNodeTypes = resetCoil

复位线圈会排在普通线圈之前，但拓扑不允许复位线圈时，排序规则不会凭空创建它。

最终诊断中的 score 通常由四部分组成：

    topology          基础拓扑合理性分
    rankingRules      本节规则贡献
    businessEvidence  术语、角色和业务规则证据
    businessChain     可靠业务链附加分


十五、规划中的能力
----------------

1. plannedRules

作用：记录业务上有价值，但当前输入数据或建议协议还不足以可靠实现的能力。
这些条目不会产生 suggestion。

子字段：

    capabilityNeeded  真正实现前还缺哪些结构化能力
    fallback          当前版本采取的保守行为

例子：

    capabilityNeeded = [
      "multiNodeSuggestion",
      "templateInstantiation",
      "parameterBinding"
    ]

表示要一次生成完整电机/阀门/气缸模板，还需要多节点建议协议、模板实例化和参数绑定。
当前只能继续每次补一个节点。

其他典型规划边界：

    状态机归属       缺少 SFC/状态机/设备 FB 元数据，不判断逻辑应该写在哪里
    安全功能         缺少风险评估和安全验证，不自动生成或旁路安全逻辑
    PID 工程设计     不自动整定参数，也不证明量程和采样周期正确
    项目库可用性     只保证元素存在于本地库数据，不保证目标 PLC 工程已加载对应库


十六、把几个字段串起来看一个完整例子
----------------------------------

场景：用户选中 Stop_Request，上游/同组有 Feed_Axis，当前链中还没有 MC_Stop。

1. termPatterns

    Stop_Request -> stop、commandSignal 相关文字证据

2. variablePatterns / blockPortRoleRules

    Stop_Request 被识别为 commandSignal
    Feed_Axis: AXIS_REF 被识别为 axisReference
    Deceleration 参数被识别为 deceleration

3. derivedTerms

    AXIS_REF -> axis、motion

4. loopSignatures

    同一组具备 axisReference + commandSignal + deceleration
    同组尚未存在 MC_Stop
    因而命中 MC_Stop completion 签名

5. libraryRules

    signatureRefsAny 命中上述签名
    requiredTypeCapabilities 确认运动轴能力
    candidateNames 选择 MC_Stop
    portRequirements 检查 Axis、Execute、Deceleration 等真实端口和类型

6. businessChainGuards

    检查同一能力是否已经存在，避免重复推荐；同时不允许候选绕过可靠联锁条件。

7. rankingRules / businessChainEnhancement

    在合法候选之间进行排序；可靠业务链只给已有业务证据的候选增加链路分。

8. presentation

    返回业务化 title/text，并说明这是受控停止以及 Execute 的使用语义。


十七、修改规则时最容易犯的错误
------------------------------

1. 只加关键词，不加排除词，导致 TON/TOF/TP 或 MC_Stop/MC_Halt 相互误报。
2. 只看变量名，不检查 acceptedDataTypes，把 BOOL、TIME、REAL 的角色混在一起。
3. 把同一个 POU 当成同一个回路，造成不同设备或不同工位变量误配。
4. candidateNames 写了库中不存在的块，前端无法渲染真实端口。
5. portRequirements 只写输入，不检查规则实际依赖的关键输出端口。
6. 用 priority 当成全局总分，忽略不同规则组之间互不比较。
7. nodeIntentRules 和 contactPolarityRules 同时决定极性，造成两套规则打架。
   正确做法是极性只交给 contactPolarityRules，nodeIntentRules 只负责业务意图和文案。
8. 用 plannedRules 当成已经实现的功能。planned 条目只是能力边界记录。
9. 为单个测试案例硬编码变量名或节点 ID。规则应依赖角色、类型、设备归属和拓扑。
10. 修改规则后只测正例，不测“条件不齐、已有目标块、跨设备、类型错误”等反例。
